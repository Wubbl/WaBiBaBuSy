## FIXED Issues

### 1. Player Crash on GIF Loop #4-5
**Root Cause:** `OnMediaEndReached` callback called `_mediaPlayer.Stop()` and `Play()` synchronously from LibVLC event thread.
**Fix:** Removed Stop/Play from callback. Looping now handled only by 95% position seek in `VideoDisplayCallback`.

### 2. DXGI Flip Model Buffer Rotation
**Root Cause:** D2D render target created once, never recreated after `Present()`. Buffers rotate with FlipSequential.
**Fix:** Added `RecreateD2DRenderTarget()` called after every `Present()`.

### 3. Explorer Crash (WS_EX_TRANSPARENT)
**Root Cause:** `WS_EX_TRANSPARENT` crashes explorer.exe on Windows 11 24H2+.
**Fix:** Replaced with `WS_EX_LAYERED + SetLayeredWindowAttributes(0xFF)`.

### 4. Only First Frame Visible (GIF Animation)
**Root Cause:** LibVLC's image demuxer treats GIFs as static images - decodes only frame 0 and re-displays it at max speed. Even with `--demux=avformat`, Duration reports as 100ms and EndReached fires after 1 display callback. Each Stop/Play restart only produces frame 0.
**Proof:** Buffer hash (`88247DB5`) was constant across ALL display callbacks. Position stuck at `0.000`.
**Fix:** GDI+ frame pre-extraction. `ExtractGifFrames()` loads all frames using `SelectActiveFrame()`, JPEG-compresses to `List<byte[]>` (~75MB vs ~4GB raw). `GetFrameAtPosition()` decodes on-demand with single-frame cache. LibVLC still used for MP4/video.
**Additional fixes during investigation:**
- Removed `_frameLock` deadlock (seeking LibVLC while holding lock)
- Removed `input-repeat=-1` (caused rapid restart loops)
- Fixed `OnMediaEndReached` to use `ThreadPool.QueueUserWorkItem`

## OPEN Issues

### ISSUE-004: GIF/MP4 Animation Speed Too Slow (HIGH)

**Symptoms:**
- GIF animation plays but noticeably slower than expected
- MP4 video also plays too slow (confirmed working but wrong speed)
- Both media types affected - suggests a common timing/speed multiplier issue

**Suspected Root Causes:**
1. `SpeedMultiplier` from `AnimationLayerConfig` is not applied to GIF frame timing in `GetFrameAtPosition`
2. For MP4: `SpeedMultiplier` is not applied to `_mediaPlayer.Rate` in LibVLC
3. The elapsed time source (`timestampMs`) may be running slower than real-time

**Key Files:**
- `VideoWallpaperRenderer.cs` - `GetFrameAtPosition()` GIF timing, LibVLC rate
- `AnimationLayerRenderer.cs` - `UpdatePosition()`, `_currentElapsedMs`
- `WallpaperConfig.cs` - `SpeedMultiplier` property
- `D2DPlayerHost.cs` / `Program.cs` - timestamp calculation in render loop

### ISSUE-005: GIF Doesn't Loop (HIGH)

**Symptoms:**
- GIF plays through once and stops at last frame
- Render loop continues (Frame #300+) but image is static
- Logs show `Playing: True` and `ShouldCompose: True` - composition keeps running

**Suspected Root Causes:**
1. `timestampMs` passed to `GetFrameAtPosition()` keeps increasing past `_gifTotalDurationMs` - the modulo should handle this, but need to verify
2. The frame index calculation may be stuck on last frame when `accumulated` never exceeds `loopedMs`
3. The elapsed time might overflow or the modulo might not work as expected

**Key Files:**
- `VideoWallpaperRenderer.cs` - `GetFrameAtPosition()` GIF looping logic
- `AnimationLayerRenderer.cs` - `_currentElapsedMs` passed as `timestampMs`
- `Program.cs` - render loop timestamp source

### ISSUE-006: GIF Frame Extraction Slow - 8 seconds (MEDIUM)

**Symptoms:**
- `ExtractGifFrames()` takes ~8 seconds for a 500-frame GIF
- GDI+ `SelectActiveFrame()` is the bottleneck
- This blocks the UI during initialization

**Research Areas:**
1. GDI+ SelectActiveFrame performance characteristics
2. Alternative libraries: SkiaSharp, ImageMagick.NET, SixLabors.ImageSharp
3. FFmpeg-based extraction via process spawn
4. Parallel extraction strategies

**Key Files:**
- `VideoWallpaperRenderer.cs` - `ExtractGifFrames()`

### ISSUE-007: Memory Leak in D2D Player (HIGH)

**Symptoms:**
- Player.D2D.exe memory grows continuously during playback
- Memory keeps growing even after GIF animation stops at last frame
- Render loop continues composing frames even though visual output is static

**Suspected Root Causes:**
1. `GetFrameAtPosition()` returns `new Bitmap(...)` clones - caller may not dispose them
2. `ComposeForScreen()` creates bitmaps that may not be disposed after D2D conversion
3. `ConvertBitmapToD2D()` may leak D2D bitmaps
4. The composition pipeline creates intermediate bitmaps each frame without disposal

**Key Files:**
- `VideoWallpaperRenderer.cs` - `GetFrameAtPosition()` bitmap cloning
- `CompositionRenderer.cs` - `ComposeForScreen()` bitmap lifecycle
- `AnimationLayerRenderer.cs` - `RenderForScreen()` bitmap creation
- `Program.cs` - render loop bitmap handling, D2D bitmap disposal

### ISSUE-008: GIF Centering/Positioning (MEDIUM)

**Symptoms:**
- GIF is currently stretched to fill entire monitor resolution

**Implementation Notes:**
- `AnimationLayerRenderer` already has `_animationWidth`/`_animationHeight` - currently hardcoded to 16:9
- Should use actual GIF dimensions from `VideoWallpaperRenderer` after extraction
- Need a "fit mode" option: Stretch, Center (native), Fit (preserve aspect), Fill (crop)

**Key Files:**
- `AnimationLayerRenderer.cs` - `CalculateAnimationDimensionsAsync()`, `RenderForScreen()`
- `AnimationLayerConfig` model - needs FitMode property
- `VideoWallpaperRenderer.cs` - `_videoWidth`/`_videoHeight` after extraction

## Architecture Notes

### Render Pipeline Flow (Current):
```
GIF Path:
  GDI+ ExtractGifFrames() → JPEG byte[] storage
    ↓ GetFrameAtPosition(timestampMs)
  Decode JPEG → Bitmap (cached by frame index)

MP4/Video Path:
  LibVLC VideoDisplayCallback → _currentFrameBitmap
    ↓ GetFrameAtPosition(timestampMs)
  Clone bitmap

Both paths:
  AnimationLayerRenderer.RenderForScreen()
    ↓ Crops to screen viewport
  CompositionRenderer.ComposeForScreen()
    ↓ Composites background + animation
  D2DPlayer.ConvertBitmapToD2D()
    ↓ GDI+ Bitmap → D2D bitmap
  D2DPlayer._d2dRenderTarget.DrawBitmap()
    ↓ Draws to render target
  _swapChain.Present()
    ↓ Presents to screen
  RecreateD2DRenderTarget()
    ↓ Rebinds to new back buffer
```
