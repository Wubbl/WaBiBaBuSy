- **Solution:** UpdateLayeredWindow (Option 1)

**Problem:**
User sees only ONE FROZEN FRAME on desktop, despite all backend systems working correctly.

**Root Cause Identified:**
DXGI swap chain on Windows 11 24H2 does NOT update display after first Present() call when window is parented to desktop. Complete diagnosis:

**✅ Backend Pipeline Working (Verified):**
- LibVLC decoding: Frames 30 → 75 → 120... (continuous, 20 FPS)
- Manual looping: Loop #1 → #2 → #3... (working)
- Composition: GetFrameAtPosition returning different bitmaps (✅ CHANGED)
- D2DPlayer render loop: Running at 60 FPS
- SwapChain.Present(): Being called every frame
- All logs confirm continuous operation

**❌ Display Issue:**
- First frame presents successfully to screen
- Subsequent Present() calls do NOT update screen
- User sees frozen first frame
- Windows Desktop Window Manager not compositing updates

**Attempted Fixes (Did Not Work):**
1. Changed Present(1, ...) to Present(0, ...) - no vsync wait
2. Added InvalidateRect() to force compositor update
3. Both applied but screen still frozen

**Research Complete (2026-01-18):**
- ✅ Phase 1: Tested flip model swap chains (FlipSequential vs FlipDiscard) - FAILED
- ✅ Phase 2: Implemented Lively's Windows 11 24H2 parenting (WS_EX_LAYERED) - FAILED
- ✅ Phase 3: Identified root cause - Windows 11 24H2 DXGI incompatibility
- 🎯 **Solution Selected:** UpdateLayeredWindow (Option 1)
- 🔄 **Backup Plan:** DirectComposition API (Option 3)

**Implementation Plan:**
1. Copy DXGI back buffer to system memory after render
2. Call UpdateLayeredWindow() to manually paint frames
3. Fallback to Present() on Windows 10 (backwards compatible)
4. If performance issues: Try DirectComposition API

#### `TASK-009` D2DPlayer High CPU Usage (7%)
- **Status:** 🟢 FIXED (2026-02-26 - Native D2D Composition eliminates GDI+ per-frame conversion)
- **Priority:** P0 (CRITICAL - Performance Issue)
- **Date Reported:** 2026-01-09
- **Component:** D2DPlayer process render loop
- **Related Files:**
  - `WaBiBaBuSy.Player.D2D/Program.cs` (RenderLoop, line 476-599)

**Problem:**
D2DPlayer.exe process uses 7% CPU during GIF playback. Expected: <1%.

**Root Cause:**
Render loop runs at fixed 60 FPS (16ms sleep) regardless of content frame rate:
- GIFs typically 10-30 FPS
- Videos may be 24-60 FPS
- Rendering at 60 FPS for 10 FPS content wastes CPU

**Solution:**
Adaptive frame rate based on content:
- Detect GIF frame delay from metadata
- Use content-appropriate sleep duration
- For 10 FPS GIF: sleep 100ms (not 16ms)
- For 60 FPS video: sleep 16ms

**Acceptance Criteria:**
- [ ] CPU usage drops to <1% for GIF playback
- [ ] Render loop adapts to content frame rate
- [ ] No visible stuttering or frame drops
- [ ] Animation timing remains accurate

**Time Estimate:** 2-3 hours
**Blockers:** TASK-008 (need working animation first)

#### `TASK-001` Fix "Apply via Direct2D" - Simple Centered Playback
- **Status:** 🟢 Done
- **Priority:** P0 (Critical - Usability Blocker)
- **Assignee:** Dev
- **Dependencies:** None
- **Related Files:**
  - `WaBiBaBuSy.UI/ViewModels/MainWindowViewModel.cs` (Apply button handlers)
  - `WaBiBaBuSy.WallpaperEngine/Composition/CompositionRenderer.cs`
  - `WaBiBaBuSy.Core/Services/WallpaperPlaybackService.cs`
  - `WaBiBaBuSy.WallpaperEngine/Direct2D/D2DPlayerHost.cs`

**Problem:**
Currently, clicking "Apply via Direct2D" triggers the full animation system (animations moving across screen with background layers). This should ONLY happen for the "Animation" feature.

**Expected Behavior:**
When a user selects a video/GIF and clicks "Apply via Direct2D", they want **simple playback**:
- Video/GIF **centered** on the selected monitor
- **NO** movement/animation paths
- **NO** background layer composition
- Just the content playing in a loop on that monitor
- Support multi-monitor selection (same content on multiple monitors)

**Acceptance Criteria:**
- [ ] "Apply via Direct2D" shows video/GIF centered on selected monitor(s)
- [ ] No animation movement (stationary playback)
- [ ] No background layer rendering
- [ ] Content loops indefinitely on selected monitor(s)
- [ ] Multi-monitor selection works (same content on all selected monitors)
- [ ] Animation system ONLY triggers when using "Animation" feature explicitly

**Implementation Strategy:**
Create two separate code paths:
1. **Simple D2D Playback Mode**:
   - Use D2DPlayerHost directly
   - No composition pipeline
   - Just display video/GIF frames centered
   - One D2DPlayerHost per selected monitor

2. **Animation Mode** (existing):
   - Full composition pipeline
   - Background layer + animation layer
   - Movement/paths across screens
   - Triggered only from "Animation" configuration

**Time Estimate:** 3-4 hours
**Blockers:** None

## 📝 Notes & Decisions

### Architecture Decisions

**1. Two Separate Rendering Modes:**
- **Simple Playback Mode**: Direct D2DPlayerHost usage, no composition
- **Animation Mode**: Full composition pipeline with background + movement

**2. Monitor Selection:**
- Must be explicit (user selects from list)
- At least one monitor required
- Selection persists in configuration

**3. Feature Naming:**
- "Cross-Screen" is confusing → rename to "Animation"
- Clearer separation between simple playback and animation features

### Known Issues
- Windows 11 24H2+ requires separate process (✅ SOLVED)
- Desktop icon interaction requires `WS_EX_TRANSPARENT` (✅ SOLVED)
- Message pump limit of 100 messages/frame (✅ SOLVED)
