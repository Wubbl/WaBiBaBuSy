# WaBiBaBuSy — Feature Overview & Feature-Completeness Roadmap

**Created:** 2026-07-07 (full codebase audit)
**Scope:** What the animation system supports today (verified against code, not docs), and what is missing to make the original vision feature-complete: *visuals traveling from one monitor to the next across physically adjacent machines at a LAN party.*

---

## Part 1 — Currently Supported Animation Features

The live render path is the **native D2D player** (`WaBiBaBuSy.Player.D2D/Program.cs`). All visual state is a pure deterministic function of `(sharedStartTimestamp, elapsedMs, config, cell identity)` — that determinism is what synchronizes machines without per-frame network traffic.

### Movement (`MovementType`, `MovementCalculator.cs`)

| Type | Behavior | Parameters |
|---|---|---|
| Static | Centered, time-invariant | — |
| Linear | Straight A→B, loops (with tile-align snap for seamless color wrap) | Start/End, Speed, Loop, **Reversed**, **Endless** |
| Bounce | Reflects off canvas edges (fold/unfold modular math) | DirectionAngleDegrees, Speed |
| SineWave | Horizontal travel + vertical sine oscillation | WaveAmplitudePixels, WaveFrequencyHz, Reversed |
| Circular | Orbit around a center | OrbitCenter, OrbitRadiusPixels, Reversed |
| RandomWalk | Seeded waypoint wander, smoothstep interpolation, rolling seed | RandomSeed, RandomStepIntervalMs, IterationStepCount |

`Endless` (Linear + Traveling colors) = infinite scroll where cell colors never repeat on loop. IconZone mode uses a separate path-following movement engine in the player (A* path sampling + optional SineWave/RandomWalk perpendicular offsets).

### Pattern grid (`PatternConfig`, `PatternLayout`)
Tiles the animation into an infinite deterministic world-space grid; each cell has a stable `(LogicalI, LogicalJ)` identity. Sizing: `Fill` (auto) or `Explicit` (CountX/CountY). Per-cell stable jitter: `RandomOffsetMaxPx`, `RandomRotationMaxDeg`, `Seed`. Multi-image: deterministic per-cell `SourceIndex` from `AdditionalAnimationPaths`. **Not supported for video content.**

### Color grading (`ColorGradingMode`, `ColorGrader`)
Monochrome-logo tinting via D2D ColorMatrix (luminance × tint, alpha preserved).

- **Time-based (whole layer, per frame):** `None`, `Rainbow` (hue sweep), `RandomColors` (seeded pick from ColorList), `Gradient` (ping-pong A↔B), `CycleColorList`
- **Traveling (per cell, time-independent — colors travel with the element):** `TravelingRainbow` (hash → hue), `TravelingList` (diagonal stripes), `TravelingRandom` (scattered)
- `ColoredCellPercentage` — deterministic fraction of cells that get color; rest stay monochrome

### Backgrounds (`BackgroundMode`)

| Mode | Description |
|---|---|
| SolidColor | Hex fill (with auto-detection from wallpaper edge pixels in UI) |
| StretchedImage / TiledImage | Image background |
| ThreeZone | Top zone / darker middle corridor / bottom zone — corridor constrains animation Y |
| IconZone | Zones derived from **real desktop icon positions**; A* (`ZonePlanner`) routes the animation through icon-free space; feathered fades, zone merge/expansion |

### Content types

| Content | Path | Notes |
|---|---|---|
| GIF | Magick.NET → GPU-resident `ID2D1Bitmap[]`, per-frame delays, SpeedMultiplier | Full feature support |
| Video (mp4/avi/mkv/mov/wmv/webm/flv) | LibVLC → raw buffer → `CopyFromMemory` → D2D bitmap | Working (placeholder era is over). No pattern/multi-image/traveling colors |
| Static image (jpg/png/bmp) | Single-frame via GIF pipeline | Full feature support |

### Distribution & multi-machine traversal
- **Modes:** `Sequential` (one virtual canvas spanning all nodes; visuals flow node→node) and `Simultaneous` (each monitor independent). (The unimplemented `GroupedSequential` enum value was removed 2026-07-18.)
- **Virtual canvas:** `VirtualCanvasManager` lays out local monitors + remote clients left-to-right by user-defined order, inserting **bezel/physical-distance gaps** (`PhysicalDistanceCm × PixelsPerCm`).
- **Traversal mechanism:** no handoff — every player independently computes the same world state from the shared UTC start timestamp and subtracts its own `monitorOffsetX`. A sprite exiting one machine's slice naturally enters the next.
- **IconZone sequential:** one global A* path is computed server-side across the full virtual width and shipped as `PrecomputedPath`; regenerated per lap via `SIGNAL:LAP_COMPLETE`.
- **Topology UI:** drag ordering, Ctrl+multi-select, physical distance editing, refresh-rate display with mismatch warning, animation state indicators.
- **Fit/placement:** `ContentFitMode` (Stretch/Center/Fit/Fill), `VerticalAlignment` (Top/Center/Bottom), centered simple-playback mode.
- **Debug overlay** (F11 or IPC): A* path, icon rects, zone band outlines, movement trail (180 samples), info panel.

### What does NOT exist today (confirmed absent)
- Playlist / rotation / scheduling of animations (one config at a time)
- Transition effects (`transition_effect` proto field is never used)
- Clock-offset compensation between machines (assumes synced Windows clocks)
- Auto-reconnection
- Server-browser UI for mDNS discovery (backend works)
- Audio reactivity, interactivity
- Pattern/traveling colors on video content

## Part 2 — Feature-Completeness Roadmap

Ordered by impact on the LAN-party vision. Tier 1 items are the difference between "demo that works on my desk" and "works on 10 friends' machines."

### Tier 1 — Make the traveling-visuals promise reliable across real machines

1. **Remote parameter parity (P0, small effort, huge payoff).** Serialize the full `MovementConfig` as `movement_json` (exactly like `pattern_json`/`color_grading_json`) and send `AnimationLayerConfig` sizing (TargetHeight etc.). Today remotes rebuild movement from an int + defaults, so any non-default wave/orbit/reversed/endless setting desyncs remote machines. Same for backgrounds: only a solid color reaches remotes — add ThreeZone/IconZone/image background transport (proto enum or JSON).
2. **Fix Simultaneous mode on remotes.** Don't send explicit canvas/offset overrides when `per_monitor_mode=true` (or have the client ignore them) so the documented invariant holds on remote machines.
3. **Clock-offset estimation.** NTP-style 4-timestamp exchange over the existing heartbeat (client send time, server receive/send, client receive → offset + RTT). Apply the offset when converting `shared_start_timestamp_ms` to the local render epoch. Without this, ±50ms is only achievable if every machine runs tight NTP.
4. **Auto-reconnection + session resume.** Exponential backoff (1s→30s), `ConnectionStatusChanged` on stream death, and on rejoin the server re-sends the current animation command — the epoch back-dating already makes a late joiner land at the correct position mid-animation.
5. **Dead-client sweep + write serialization.** Sweep `LastHeartbeat > 3×interval`; per-client `SemaphoreSlim` around gRPC stream writes; await server `StartAsync()` so a failed port bind is reported.
6. **Real remote monitor geometry.** Registration should carry each client's monitor resolution/count/DPI instead of assuming "same as the server's first monitor" for gap math and canvas layout.

### Tier 2 — Party experience features

7. **Playlist / Party Mode (biggest missing user feature).** A rotation list of animation configs with per-item duration and shuffle, plus scheduled "shows" (e.g. every 30 min the fish swims across all machines once, then background returns). All infrastructure (content distribution, shared timestamps) exists; this is config + orchestration + UI.
8. **Machine-entry transition effects.** The `transition_effect` proto field exists but is unused — even a subtle glow/flash when the sprite crosses a bezel gap would sell the traversal effect. Deterministic: each player knows when the sprite crosses its edge.
9. **Server browser UI.** mDNS discovery works in Core; add the "join server" dialog listing discovered servers instead of manual IP entry — big quality-of-life at a LAN party.
10. **2D topology (two table rows).** LAN parties have monitors in rows facing each other. `VirtualCanvasManager` is 1D (left-to-right). A row concept (Y offsets, snake-order traversal: end of row 1 → start of row 2) would map the real room. Movement math already supports 2D positions.
11. **Video feature parity.** Pattern tiling + traveling colors for video content (currently GIF/image only), or document it as a deliberate non-goal.
12. **Live position preview in topology.** The server can compute the same deterministic position math — show a moving dot on the topology canvas indicating where the sprite currently is ("it's on Max's machine right now").
13. ~~**`GroupedSequential`.**~~ Removed 2026-07-18 — 2D topology (item 10) covers the underlying grouping need.

### Tier 3 — Polish / long-run quality

14. **Float-precision folding** in `MovementCalculator` (fold elapsed into the movement period in double before converting to float) — prevents stutter after days of uptime; the Endless branch already does this correctly.
15. **RandomWalk seed-rotation continuity** — pin the last waypoint of an iteration to the first waypoint of the next to remove the deterministic teleport.
16. **Wire up or remove `TimingSynchronizer`** — the drift-correction loop has no callers; either integrate runtime drift telemetry (useful for the topology UI: show per-client drift) or delete it. Fix the `CalculateClockOffsetMs(ExpectedPositionMs)` → always-zero bug if kept.
17. **Dead-code cleanup.** The legacy GDI+ composition stack (`CompositionRenderer`, `AnimationLayerRenderer`, `GifWallpaperRenderer`, `CrossScreenFrameRenderer`, `VideoWallpaperRenderer`, `ImageWallpaperRendererLibVLC`) and the server-side frame-streaming gRPC path (`StreamCrossScreenFrames`, `UseDistributedRendering`) are never invoked. Archive or delete — they confuse every audit and inflate the binary.
18. **IconZone open issues** (see `.docs/2026.04_IconZoneAnimation_TODO.md`): visual band drawn at padded size, desktop right-click recovery, A* fallback crossing icons, hidden-icon positions, DirectWrite info panel, F11 reliability.
19. **Audio-reactive mode (stretch).** Beat-synced color pulses via a shared BPM + phase timestamp would stay fully deterministic across machines (no audio streaming needed — server taps audio, broadcasts beat grid).

### Suggested order of attack
1–3 first (they are small and unlock trustworthy multi-machine demos) → 4–5 (robustness for a real party) → 7 Playlist + 9 Server browser (the two most visible user features) → the rest as desired.
