# Test scenarios

Scenarios for the automated test mode (design: `.docs/plans/2026-09-30-automated-test-mode-design.md`).
The bundled files are copied next to the exe (`TestScenarios\` in the build/install folder).

## Running

1. Server: Settings > Developer > "Enable test mode", then restart the server (the flag is read when the server starts).
2. Start a run, any of:
   - Main window: `...` menu > Developer tools > **Run test suite...** (pick a scenario file).
   - CLI: `WaBiBaBuSy.UI.exe --test-run TestScenarios\sync-basic.json --exit`
     (`--exit` quits when the run is done; exit code 0 = pass, 1 = a step failed or a node is unaccounted for (lost, a probe not answered, nothing measured), 2 = aborted or could not run; the CLI waits up to 120 s for the required remote clients).
   - Local control API (127.0.0.1:50052, application/json, local paths only):
     `curl -X POST -H "Content-Type: application/json" -d "{\"scenario\":\"C:/path/TestScenarios/sync-basic.json\"}" http://127.0.0.1:50052/test/run`,
     then `curl http://127.0.0.1:50052/test/status`, `curl http://127.0.0.1:50052/test/runs`, `curl -X DELETE http://127.0.0.1:50052/test/run`.
3. Every client must have its window open and be **Connected**, with the Client setting "Answer automated test runs from the server (screenshots show only the wallpaper)" on (default on; bottom of the Client section in Settings).

## Scenarios

| File | Needs | What it checks |
|---|---|---|
| `smoke-local.json` | server only | Single-machine sanity run (~45 s): timecode strip, marker boxes, drift over 30 s, pattern parity across local monitors |
| `sync-basic.json` | 1+ client | Clean start, bezel crossing, 10 minute drift/CPU/GPU/memory series |
| `parity-matrix.json` | 1+ client | Linear, SineWave, Static, Bounce wave, pattern + traveling colors, face direction, IconZone: marker positions and exact-frame pixel parity |
| `clock-skew.json` | 1+ client | Simulated client clock skew: start and drift stay within tolerance |
| `recovery.json` | 1+ client | Fault injection (~3 min): a 6 s link loss (reconnect time after the link is back, limit 5 s) and a 45 s silence (time until the server drops the node, limit 45 s); a probe after each checks the node rejoined at the right position |
| `showcase/showcase.json` | server only | Not a pass/fail check: plays 12 showcase scenes and renders exact frames at 1/4/9/20 s as a contact sheet for tuning animation settings |
| `showcase/events.json` | server only | Not a pass/fail check: fires the five one-shot show events (Celebration, Spotlight, Traversal, Blackout — in white, so the frame differs from the dark scene —, Announce) at fixed scene times and renders exact frames inside each event; waits 3 s after the Traversal so remote clients have its image |

Without remotes, a copy of `parity-matrix.json` with `"minRemoteNodes": 0` (saved next to the original so the relative scene paths resolve) runs every step on the server's own monitors. That is a quick regression check before a multi-machine session; it does not test the network.

Room settings (Ring / Snake, facing rows, Physical units) come from the room, not from the scene. Set them before
`parity-matrix.json`, and run it twice to cover both pixel mode and Physical units.
In `clock-skew.json` and `recovery.json` replace `REMOTE-HOSTNAME-1` with a client name shown on the room tiles. With a second client, add `"<its name>": -2000` to `simulatedClockSkewMs` in `clock-skew.json` (every key must match a connected node, or the step fails).

`marker.png` (`assets/`) is generated by `tools/make-test-marker.ps1`; the scene files reference it relatively.

## Step `showEvent`

Fires a one-shot show event at a fixed scene time (a scene started by `playScene` must be running):

```json
{ "type": "showEvent", "label": "traversal cat", "atElapsedMs": 12000,
  "event": { "type": "Traversal", "durationMs": 6000, "imagePath": "assets/cat.gif", "spriteAspect": 1.0, "heightFraction": 0.4 } }
```

- `event`: a show event (`type` Spotlight / Celebration / Traversal / Blackout / Announce, `durationMs`, `targetOrder` for Spotlight, `colorHex`, `seed`, `text` + `spriteAspect` for Announce, `imagePath`, `heightFraction`).
- `atElapsedMs`: the event's T0 on the scene clock; an `exactFrame` with `elapsedMs` inside `[atElapsedMs, atElapsedMs + durationMs]` shows it.
- `imagePath` is relative to the scenario file. The runner assigns `eventId` (a fresh id per run) and `t0Utc` itself.

## Step `fault`

Injects a fault on one remote client and measures the recovery from the server's side (design §12):

```json
{ "type": "fault", "label": "10 s link loss", "node": "PC-02", "fault": "drop", "ms": 10000, "maxReconnectMs": 5000 }
{ "type": "fault", "label": "power-off stand-in", "node": "PC-02", "fault": "silent", "ms": 45000, "maxSweepMs": 45000 }
```

- `node`: tile name (case-insensitive) or client id; a name shared by two tiles fails the step (use the client id), and a node lost earlier in the run cannot be faulted. `fault`: `drop` (the client tears its link down and cannot reach the server for `ms`, then reconnects through its real backoff) or `silent` (no heartbeats, responses or thumbnails for `ms`; the connection stays open, as with a powered-off machine). `ms` must be 1 000–120 000 (checked when the scenario loads). The client ignores faults when "Answer automated test runs" is off.
- The runner watches the server's client registry every 250 ms. drop: `reconnectMs` = back − (sent + `ms`); pass ≤ `maxReconnectMs`, warn ≤ 2×, fail later or never. silent: `sweepMs` = dropped − sent; pass ≤ `maxSweepMs` and back afterwards, warn if dropped late, fail if never dropped or never back (a node still listed 15 s after its silence ended fails right then).
- The outage is expected: the node is not listed under "Node failures", its test mode is re-sent after the reconnect, and later probes include it again. Put a `wait` of a few seconds before the next probe so the scene has restarted on the node.
- `report.html` lists every fault in a **Faults** table.
- Reconnect attempts come 0 / 1 / 3 / 7 / 15 / 31 s after the link is lost (backoff 1, 2, 4, 8, 16, 30 s), so the reconnect time depends on where the outage ends: `recovery.json` uses 6 s (next attempt at 7 s → about 1 s after the link is back, a stable verdict). An outage of 8–15 s waits up to 7 s for the 15 s attempt; edit `ms` to measure such a gap.

## Results

`%LOCALAPPDATA%\WaBiBaBuSy\TestRuns\<yyyy-MM-dd_HHmm>_<scenario>\` holds `report.json`, `report.html`,
`nodes\<node>\*.png` (captures) and `logs\<node>.log`. `report.html` is self-contained: overall verdict, a per-step
table, a drift chart per node, the annotated captures (timecode strip, detected marker boxes, expected vs found positions)
and CPU/GPU/memory against the thresholds. The 200 MB memory threshold applies to remote clients only; on a single machine the server's memory is reported but not thresholded.

## Showcase and playlist presets

`showcase/scenes/` holds curated party scenes (BiBaBu logo, cat GIF; `12-lunar-tears` points at a video outside the repo).
`showcase/playlist-presets.json` groups them into playlists; `dotnet run tools/build-playlist-presets.cs` writes them to
`%APPDATA%\WaBiBaBuSy\playlists\` (Playlist tab). Sequential stills only cover the parts of the canvas your monitors show:
with a multi-row room the turn gap is empty canvas, so single sprites are often between monitors.
